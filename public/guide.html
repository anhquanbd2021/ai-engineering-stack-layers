Layer guide

8 questions, one tool slot each

The stack is a set of questions, not a parts catalog. Each layer exists to answer exactly one — and each carries a concrete failure when a requirement exists but the layer doesn't.

Opinionated defaults, honest limits. The tool picks are current answers to each question, not endorsements — tools rotate, the layers don't.

Start here

What this demo proves

An empty requirement set lights exactly one layer — the model — because every AI app answers that question even by defaulting. The weekend-chatbot preset activates two of eight layers, and that minimal map is correct, not incomplete. The support-agent preset demands seven; only the full lab activates all eight.

Runtime layers

Layers that ship inside the app

Layer 1

Frontend

“How does a human touch this?” Prototype UI (Streamlit) and product UI (Next.js) are different answers to the same question.

Skip-failure
A script only its author can run — or weeks of UI before anyone validated the feature.
Layer 2

Orchestration

“Who decides what happens next?” LangGraph for state-machine graphs, CrewAI for role-based crews.

Skip-failure
if-chains around LLM calls nobody can trace — or a graph runtime carrying a single prompt.
Layer 3

Retrieval (RAG)

“How does the model learn your data?” Documents → embeddings → vector DB → the most relevant chunks enter the prompt.

Skip-failure
Confident fiction — or 40 KB of context re-sent per request.
Layer 4

Model (LLM)

“Which model does the thinking, on whose hardware?” Ollama + open weights for local control; hosted APIs for capability and zero ops.

Skip-failure
The choice made by a tutorial instead of latency, cost, and privacy requirements.
Layer 5

Tools (MCP)

“How does the model act on the world?” One protocol to GitHub, Slack, databases, and internal APIs.

Skip-failure
A read-only advisor humans copy-paste for — or bespoke shims per service.
Layer 7

Data + Observability

“Where does state live, and can you see inside a run?” SQLite/DuckDB/Supabase for persistence; Phoenix for traces.

Skip-failure
Bug reports you cannot reconstruct; a user report as your monitoring channel.
Layer 8

Deployment

“How does it leave your laptop?” Docker for identical-anywhere packaging; Workers/Hugging Face for light on-ramps.

Skip-failure
A demo video instead of a URL — the learning loop never starts.

Dev-time layer

Layer 6 is around the app, not in it

Layer 6

Code Agents

“Who writes the code — including this app's?” Claude Code and Aider build the system; they never ship inside it.

Skip-failure
A permanently slower loop between “the demo works” and “the system works.”

Run locally

Inspect the evidence

npm test        # mapper + preset sync + server
npm run scan    # side-by-side layer report on examples/
npm run check   # both
npm start       # serve the lab on :3000

Tick requirements in the lab and watch layers activate — the map you end up with should look exactly as complicated as your requirements.

Limits

What this demo does not claim

  • Tool picks are opinionated current defaults, not endorsements — the layer questions are the durable part.
  • The map models which layers exist, not configuration, capacity, or cost.
  • Requirements are binary toggles; real thresholds (QPS, document volume, latency budgets) would shift the same layers' tool picks, not the layer list.
  • A checked requirement proves a layer belongs — it does not prove the tool inside it is the right choice for your constraints.
